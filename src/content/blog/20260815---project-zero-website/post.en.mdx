## Why start with a website?

I plan to learn about AI and agents through a series of projects. Project 0 is not an AI project. It is the website that will record everything I learn afterward.

I began with almost no programming or engineering experience, so building the website is itself part of the learning process.

## What I have completed

- Installed and used Bun to run the project
- Learned the basic structure of an Astro project
- Changed the site title, author, description, and GitHub links
- Created a Chinese-first bilingual structure
- Simplified the Home, About, Blog, and Notes pages
- Removed the template's sample articles, assets, and features I do not currently need
- Disabled comments, analytics, and database-related features
- Reviewed licenses for fonts, icons, and third-party resources
- Used Git to record and push each stage of the work
- Deployed the website with Vercel and checked the production build
- Configured the site address, canonical URLs, sitemap, and RSS
- Established a workflow from drafting and branch previews to production publication

## What I have learned

### Configuration and content are different

Configuration controls site-wide behavior such as titles, languages, and navigation. Markdown and MDX files contain the actual articles.

### Checking is more reliable than guessing

When something breaks, error messages, file searches, and Git diffs usually reveal where the problem started.

### Small changes are easier to debug

After each related group of changes, I validate and commit the result. This makes it easier to identify the cause of a later problem.

### Local success does not guarantee deployment success

Although all local checks and builds passed, the first Vercel deployment still failed because of a Node.js version incompatibility. The deployment log showed that the older adapter did not recognize Node.js 24 and incorrectly fell back to the unsupported Node.js 18 runtime.

I fixed this by explicitly selecting Node.js 22 in `package.json`. This was my first practical example of how local and deployment environments can differ, and why deployment logs are important.

## From draft to publication

This blog uses Git branches and Vercel Preview deployments to reduce the risk of publishing mistakes.

1. Keep the `main` branch as the version used by the production website.
2. Create a new working branch for an article or website change.
3. Edit the Chinese and English content locally, using `draft` to control whether the article is included in the build.
4. Run the local website and check the content, layout, language switching, and links.
5. Run the project checks, tests, and production build.
6. Commit and push the working branch so Vercel creates a separate Preview website.
7. Review the Preview and then merge the branch into `main` to trigger the production deployment.

A published article can still be edited later through another branch. To temporarily remove an article, I can change `draft` back to `true` in both language versions and follow the same preview and merge workflow.

This process taught me that writing and website changes can be versioned, checked, previewed, and released in the same way as code.
