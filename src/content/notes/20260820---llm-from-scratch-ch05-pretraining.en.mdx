Chapter 4 assembled a GPT model, but all its parameters were random. Chapter 5 turns that architecture into a language model that can make meaningful predictions:

```text
unlabeled text
  → input tokens and next-token targets
  → GPT logits
  → cross-entropy loss
  → backpropagation and AdamW updates
  → trained weights
  → greedy or probabilistic text generation
```

The second half of the chapter takes a useful shortcut: instead of pretraining a large model ourselves, it maps OpenAI’s published GPT-2 weights into the architecture built in Chapter 4.

## 1. Starting from an untrained model

The notebook imports the model and simple generation function from Chapter 4:

```python
import torch

from GPTmodel import GPTModel, generate_text_simple

GPT_CONFIG_124M = {
    "vocab_size": 50257,
    "context_length": 256,
    "emb_dim": 768,
    "n_heads": 12,
    "n_layers": 12,
    "drop_rate": 0.1,
    "qkv_bias": False,
}

torch.manual_seed(123)
model = GPTModel(GPT_CONFIG_124M)
model.eval()
```

The architecture is similar to GPT-2 small, although the notebook uses a shorter context length of 256 to reduce memory and computation during the demonstration.

Setting the random seed makes the initialization reproducible. Calling `model.eval()` disables training-only behavior such as dropout; it does not train the model.

With random weights, generation produces token-shaped noise:

```python
import tiktoken

def text_to_token_ids(text, tokenizer):
    encoded = tokenizer.encode(text, allowed_special={"<|endoftext|>"})
    return torch.tensor(encoded).unsqueeze(0)

def token_ids_to_text(token_ids, tokenizer):
    flat = token_ids.squeeze(0)
    return tokenizer.decode(flat.tolist())
```

The two helper functions make the boundary between text and tensors explicit:

| Direction                | Shape or type                     |
| ------------------------ | --------------------------------- |
| text → tokenizer         | Python string → list of token IDs |
| list → model input       | `[seq_len]` → `[1, seq_len]`      |
| model output → tokenizer | `[1, seq_len]` → flat list        |
| tokenizer → text         | token IDs → Python string         |

The extra first dimension is the batch dimension expected by `GPTModel`.

## 2. Turning next-token prediction into a loss

Language-model pretraining does not require human-written labels. The labels come from the text itself by shifting the sequence one position:

```text
input:   Every  effort  moves  you
target:  effort moves   you    forward
```

At every position, the model must predict the token that follows. For a batch of token IDs with shape
`[batch_size, seq_len]`, the model returns logits with shape:

```text
[batch_size, seq_len, vocab_size]
```

For GPT-2, `vocab_size = 50,257`. Every position therefore has one raw score for every possible next token.

The notebook uses cross-entropy:

```python
def calc_loss_batch(input_batch, target_batch, model, device):
    input_batch = input_batch.to(device)
    target_batch = target_batch.to(device)

    logits = model(input_batch)
    loss = torch.nn.functional.cross_entropy(
        logits.flatten(0, 1),
        target_batch.flatten(),
    )
    return loss
```

The important shape conversion is:

```text
logits:  [batch, seq_len, vocab_size]
          ↓ flatten dimensions 0 and 1
         [batch × seq_len, vocab_size]

targets: [batch, seq_len]
          ↓ flatten
         [batch × seq_len]
```

Cross-entropy treats each token position as one classification example. It applies log-softmax internally, selects the target token’s log probability, and averages the negative values.

A lower loss means the model assigns more probability to the actual next tokens. Perplexity is another common interpretation:

$$
\text{perplexity} = e^{\text{loss}}.
$$

For a random model, the expected loss is close to $\ln(50{,}257) \approx 10.82$. The notebook’s initial losses of about 10.99 are consistent with almost-uniform predictions.

## 3. Preparing training and validation data

The sample corpus is Edith Wharton’s “The Verdict,” containing 5,145 GPT-2 tokens in the notebook run.

```python
with open("the-verdict.txt", "r", encoding="utf-8") as f:
    text_data = f.read()

train_ratio = 0.90
split_idx = int(len(text_data) * train_ratio)
train_data = text_data[:split_idx]
val_data = text_data[split_idx:]
```

The split is performed before building sliding windows. This matters because it keeps validation text out of the training examples.

```python
from create_dataloader import create_dataloader_v1

torch.manual_seed(123)
train_loader = create_dataloader_v1(
    train_data,
    batch_size=2,
    max_length=GPT_CONFIG_124M["context_length"],
    stride=GPT_CONFIG_124M["context_length"],
    drop_last=True,
    shuffle=True,
    num_workers=0,
)

val_loader = create_dataloader_v1(
    val_data,
    batch_size=2,
    max_length=GPT_CONFIG_124M["context_length"],
    stride=GPT_CONFIG_124M["context_length"],
    drop_last=True,
    shuffle=False,
    num_workers=0,
)
```

The training loader shuffles examples, while the validation loader keeps a stable order. A stride equal to the context length creates non-overlapping training windows.

Because this corpus is tiny, it is useful for learning the mechanics but not for training a general-purpose LLM.

## 4. Averaging loss across a data loader

`calc_loss_loader` evaluates more than one batch:

```python
def calc_loss_loader(data_loader, model, device, num_batches=None):
    total_loss = 0.0

    if len(data_loader) == 0:
        return float("nan")

    if num_batches is None:
        num_batches = len(data_loader)
    else:
        num_batches = min(num_batches, len(data_loader))

    for i, (input_batch, target_batch) in enumerate(data_loader):
        if i >= num_batches:
            break
        loss = calc_loss_batch(input_batch, target_batch, model, device)
        total_loss += loss.item()

    return total_loss / num_batches
```

The optional `num_batches` parameter makes frequent evaluation cheaper. During training, evaluating the full dataset after every few updates would interrupt the optimization loop for too long.

The initial notebook run produced:

| Split      | Initial loss |
| ---------- | -----------: |
| Training   |       10.988 |
| Validation |       10.981 |

These similar values are expected before training because both sets see the same random model.

## 5. Separating evaluation from training

Evaluation should not build gradients or apply dropout:

```python
def evaluate_model(model, train_loader, val_loader, device, eval_iter):
    model.eval()
    with torch.no_grad():
        train_loss = calc_loss_loader(
            train_loader, model, device, num_batches=eval_iter
        )
        val_loss = calc_loss_loader(
            val_loader, model, device, num_batches=eval_iter
        )
    model.train()
    return train_loss, val_loss
```

There are three separate ideas here:

- `model.eval()` switches modules such as dropout to evaluation behavior.
- `torch.no_grad()` prevents construction of the autograd graph and saves memory.
- `model.train()` restores training behavior before optimization resumes.

The final call needs parentheses. Writing only `model.train` refers to the method object but does not call it.

## 6. The training loop

The core pretraining loop is short because PyTorch handles automatic differentiation:

```python
def train_model_simple(
    model,
    train_loader,
    val_loader,
    optimizer,
    device,
    num_epochs,
    eval_freq,
    eval_iter,
    start_context,
    tokenizer,
):
    train_losses, val_losses, track_tokens_seen = [], [], []
    tokens_seen, global_step = 0, -1

    for epoch in range(num_epochs):
        model.train()

        for input_batch, target_batch in train_loader:
            optimizer.zero_grad()
            loss = calc_loss_batch(
                input_batch, target_batch, model, device
            )
            loss.backward()
            optimizer.step()

            tokens_seen += input_batch.numel()
            global_step += 1

            if global_step % eval_freq == 0:
                train_loss, val_loss = evaluate_model(
                    model,
                    train_loader,
                    val_loader,
                    device,
                    eval_iter,
                )
                train_losses.append(train_loss)
                val_losses.append(val_loss)
                track_tokens_seen.append(tokens_seen)
                print(
                    f"Ep {epoch + 1} (Step {global_step:06d}): "
                    f"Train loss {train_loss:.3f}, "
                    f"Val loss {val_loss:.3f}"
                )

        generate_and_print_sample(
            model, tokenizer, device, start_context
        )

    return train_losses, val_losses, track_tokens_seen
```

Each batch performs four essential operations:

1. `optimizer.zero_grad()` clears gradients left by the previous batch.
2. The forward pass and cross-entropy produce a scalar loss.
3. `loss.backward()` calculates a gradient for every trainable parameter.
4. `optimizer.step()` uses those gradients to update the parameters.

The notebook uses AdamW:

```python
optimizer = torch.optim.AdamW(
    model.parameters(),
    lr=0.0004,
    weight_decay=0.1,
)
```

AdamW adapts the update size for each parameter, while weight decay discourages weights from growing without bound.

## 7. Reading the learning signal

During the notebook run, training loss fell quickly. Generated text changed from random fragments to punctuation and repeated common phrases, then began to imitate the small corpus.

This demonstrates two different facts:

- The optimization pipeline works: the model is learning statistical patterns.
- A tiny corpus encourages memorization and overfitting rather than broad language ability.

Training and validation loss should be interpreted together. If training loss keeps falling while validation loss stops improving or rises, the model is becoming better at the training text without improving on unseen text.

The generated samples are a qualitative check. Loss is the optimization target; samples help reveal repetition, incoherence, and memorization that a single scalar can hide.

## 8. Temperature and top-k sampling

Greedy decoding always selects the token with the largest logit. It is reproducible but can become repetitive. Chapter 5 adds two controls:

```python
def generate(
    model,
    idx,
    max_new_tokens,
    context_size,
    temperature=0.0,
    top_k=None,
    eos_id=None,
):
    for _ in range(max_new_tokens):
        idx_cond = idx[:, -context_size:]

        with torch.no_grad():
            logits = model(idx_cond)

        logits = logits[:, -1, :]

        if top_k is not None:
            top_logits, _ = torch.topk(logits, top_k)
            threshold = top_logits[:, -1]
            logits = torch.where(
                logits < threshold,
                torch.tensor(float("-inf"), device=logits.device),
                logits,
            )

        if temperature > 0.0:
            logits = logits / temperature
            probs = torch.softmax(logits, dim=-1)
            idx_next = torch.multinomial(probs, num_samples=1)
        else:
            idx_next = torch.argmax(logits, dim=-1, keepdim=True)

        if eos_id is not None and (idx_next == eos_id).all():
            break

        idx = torch.cat((idx, idx_next), dim=1)

    return idx
```

### Temperature

Temperature rescales logits before softmax:

$$
p_i = \operatorname{softmax}\left(\frac{z_i}{T}\right).
$$

- `T < 1` sharpens the distribution and makes high-probability tokens more dominant.
- `T = 1` leaves the original distribution unchanged.
- `T > 1` flattens the distribution and increases variety.
- `T = 0` is handled separately with argmax because division by zero is undefined.

### Top-k

Top-k keeps only the `k` largest logits and sets every other logit to negative infinity. After softmax, filtered tokens receive probability zero.

Temperature changes the relative probabilities; top-k changes which tokens are allowed at all. Combining both constrains sampling while retaining some variety.

## 9. Saving and restoring checkpoints

`state_dict` contains a mapping from parameter names to tensors:

```python
torch.save(model.state_dict(), "model.pth")

restored_model = GPTModel(GPT_CONFIG_124M)
state = torch.load("model.pth", map_location=device)
restored_model.load_state_dict(state)
restored_model.eval()
```

To resume training faithfully, save the optimizer state as well:

```python
torch.save(
    {
        "model_state_dict": model.state_dict(),
        "optimizer_state_dict": optimizer.state_dict(),
    },
    "model_and_optimizer.pth",
)
```

The optimizer state includes AdamW’s moving averages and step counters. Loading only the model weights is enough for inference, but it does not fully restore the previous optimization process.

The model configuration is also part of the checkpoint contract. A state dictionary for one embedding size, layer count, or vocabulary size cannot be loaded into an incompatible architecture.

## 10. Matching the published GPT-2 architecture

The book’s downloader returns both metadata and arrays from OpenAI’s GPT-2 checkpoint. The architecture must be configured to match those arrays:

```python
model_configs = {
    "gpt2-small (124M)": {
        "emb_dim": 768,
        "n_layers": 12,
        "n_heads": 12,
    },
    "gpt2-medium (355M)": {
        "emb_dim": 1024,
        "n_layers": 24,
        "n_heads": 16,
    },
    "gpt2-large (774M)": {
        "emb_dim": 1280,
        "n_layers": 36,
        "n_heads": 20,
    },
    "gpt2-xl (1558M)": {
        "emb_dim": 1600,
        "n_layers": 48,
        "n_heads": 25,
    },
}

model_name = "gpt2-small (124M)"
new_config = GPT_CONFIG_124M.copy()
new_config.update(model_configs[model_name])
new_config.update({
    "context_length": 1024,
    "qkv_bias": True,
})

gpt = GPTModel(new_config)
```

Two details differ from the small model used for the local training demonstration:

- Published GPT-2 uses a context length of 1,024.
- Its query, key, and value projections include bias vectors.

Loading weights is possible only when every destination tensor has the expected shape.

## 11. Assigning and translating checkpoint weights

A small helper makes shape mismatches fail loudly:

```python
def assign(left, right):
    if left.shape != right.shape:
        raise ValueError(
            f"Shape mismatch: left {left.shape}, right {right.shape}"
        )
    return torch.nn.Parameter(torch.tensor(right))
```

OpenAI’s original TensorFlow checkpoint and the Chapter 4 PyTorch model organize some weights differently. The loading function is therefore a translation layer, not just a file copy.

The most important example is the combined QKV projection:

```python
q_w, k_w, v_w = np.split(
    params["blocks"][b]["attn"]["c_attn"]["w"],
    3,
    axis=-1,
)

gpt.trf_blocks[b].att.W_query.weight = assign(
    gpt.trf_blocks[b].att.W_query.weight,
    q_w.T,
)
```

For GPT-2 small, the checkpoint’s combined matrix has shape `[768, 2304]`, where
`2304 = 3 × 768`. Splitting the last dimension creates one matrix each for query, key, and value.

The transpose is necessary because:

| Framework representation   | Linear weight layout                |
| -------------------------- | ----------------------------------- |
| TensorFlow checkpoint      | `[input_features, output_features]` |
| PyTorch `nn.Linear.weight` | `[output_features, input_features]` |

The complete mapping is:

| OpenAI checkpoint     | Chapter 4 model                  |
| --------------------- | -------------------------------- |
| `wpe`                 | `pos_emb.weight`                 |
| `wte`                 | `tok_emb.weight`                 |
| `attn.c_attn.w`       | query, key, and value weights    |
| `attn.c_attn.b`       | query, key, and value biases     |
| `attn.c_proj`         | attention output projection      |
| `mlp.c_fc`            | first feed-forward linear layer  |
| `mlp.c_proj`          | second feed-forward linear layer |
| `ln_1`                | first block normalization        |
| `ln_2`                | second block normalization       |
| top-level `g` and `b` | final normalization              |
| `wte` again           | output head                      |

Only feed-forward layers 0 and 2 receive weights because layer 1 is GELU, which has no trainable parameters.

Reusing `wte` for the output head implements weight tying: the token embedding and output projection share the same learned vocabulary representation.

## 12. From random output to pretrained output

After loading the GPT-2 weights, the same prompt produces coherent language. In the notebook, sampling from “Every effort moves you” yielded:

> Every effort moves you toward finding an ideal new way to practice something!

This difference is not caused by changing the Python class. The architecture is almost the same; the useful behavior resides in the learned parameter values.

That is the central lesson of this chapter:

```text
architecture defines what can be learned
data supplies the learning signal
optimization changes the parameters
parameters store the learned behavior
decoding controls how predictions become text
```

## 13. Final understanding

My main takeaways are:

1. Language-model targets are created by shifting ordinary text by one token.
2. Cross-entropy compares every position’s vocabulary logits with its actual next token.
3. Training alternates forward pass, loss, backpropagation, and optimizer update.
4. Training loss, validation loss, and sample generations reveal different aspects of progress.
5. Temperature and top-k affect decoding, not the model’s learned weights.
6. A useful checkpoint includes compatible architecture information; resuming training also requires optimizer state.
7. Loading GPT-2 weights requires an explicit mapping between TensorFlow checkpoint arrays and PyTorch parameters.

Chapter 6 builds on the pretrained GPT-2 weights and adapts the model to a supervised classification task.
